# 数据、记忆与检索

## 本地数据保存在哪里

应用数据目录默认是系统 appData 下的 `Hikari`，数据库文件名为 **`hakari.sqlite`**。文件名沿用当前实现，不是 `hikari.sqlite`。

| 系统    | 默认文件                                                                  |
| ------- | ------------------------------------------------------------------------- |
| macOS   | `~/Library/Application Support/Hikari/hakari.sqlite`                      |
| Windows | `%APPDATA%\Hikari\hakari.sqlite`                                          |
| Linux   | 通常为 `~/.config/Hikari/hakari.sqlite`，实际位置由 Electron appData 决定 |

`HIKARI_DATA_DIR` 可指定独立目录；兼容旧的 `FORGE_DATA_DIR`，新配置使用前者。启动时若目标不存在，会寻找旧名称数据库，使用 SQLite backup 包含 WAL 中已提交的数据，检查完整性后发布新文件，保留原文件。目标数据库已存在时不会覆盖。

数据库使用 WAL。备份时使用 SQLite 的一致性备份功能，或退出 Hikari 后复制；运行时只复制主文件可能遗漏 WAL 中尚未检查点化的数据。

## 用 DataGrip 查看

新建 **SQLite** 数据源，选择实际的 `hakari.sqlite` 文件并连接。SQLite 是本地文件，不需要主机、端口或应用账户。首次使用时按 DataGrip 提示安装 SQLite 驱动。排查时优先使用只读连接或副本，不要直接修改运行中的检查点、权限或版本字段。

所有表采用 `id`、`owner`、`version`、`data`、`updated_at` 记录结构，桌面数据的 `owner` 是 `local`。业务对象保存在 JSON 文本 `data` 中。可用以下只读查询：

```sql
SELECT id, version, updated_at, data
FROM tasks WHERE owner = 'local'
ORDER BY updated_at DESC LIMIT 20;

SELECT id, data FROM messages
WHERE owner = 'local'
  AND (id LIKE 'memory:%' OR id LIKE 'checkpoint:%');
```

| 记录                                  | 用途                                 |
| ------------------------------------- | ------------------------------------ |
| `tasks`、`events`、`changes`          | 任务快照、事件和改动审阅状态         |
| `messages` / `checkpoint:<taskId>`    | 可恢复的执行状态                     |
| `messages` / `memory:<scope>`         | 项目长期记忆                         |
| `messages` / `vectors:<scope>`        | 检索向量缓存                         |
| `tool_calls` / `output:<taskId>:<id>` | 大型工具输出，按页读取               |
| `model_configs`                       | UI 偏好、加密模型配置和 MCP 凭据记录 |
| `grants`、`workspaces`                | 持久授权与最近打开的项目             |

系统安全存储可用时，模型密钥与 MCP 令牌加密保存；不可用时仅保存在当前进程内存。项目内容、任务、记忆和工具输出并非全库加密。向量缓存属于本地数据，不是单独的向量数据库。

## 三类记忆的实现

| 概念       | 当前实现                                                                    | 持久化边界                                                                             |
| ---------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 短期上下文 | `ContextManager` 保存模型消息、工具调用与观察；追问装入关联历史             | 原始历史在任务记录中，恢复依赖检查点；超预算上下文会压缩，不能承诺所有历史始终发给模型 |
| 工作记忆   | `MemoryManager` 存放原目标、当前计划、摘要、决策与待办，runner 管理运行状态 | `RunnerCheckpoint` 保存消息、工作记忆、预算、待回答问题和工作流阶段                    |
| 长期记忆   | `remember` / `search_memory`，按项目 scope 保存标题、内容、来源和过期时间   | `LocalPersistence.memories` 写入 SQLite；独立工作树使用原项目 scope                    |

长期记忆不是自动保存全部聊天。Agent 通过需授权的 `remember` 保存有用事实；也可在 **项目聊天 → 记忆与扩展** 查看、编辑和删除。每个 scope 最多 100 条，新任务会先按关键词选取相关记忆。过期记录保留供审阅，但不参与召回。

记忆和模型摘要都只是参考资料，可能过时或判断错误，不能覆盖用户要求或替代文件、测试证据。检查点恢复详见 [执行、验收与恢复](run-controls.md)。

## 检索如何工作

代码查找与文档 RAG 是两条不同路径。`RepositoryIndexer`、ripgrep 和 `search_code` 用于仓库文件发现、关键词匹配和文件相关性排序；当前不会自动将整个仓库向量化。

附件片段与长期记忆通过 `packages/agent-runtime/src/retrieval.ts` 检索：

1. 默认使用规范化后的词项匹配，不调用向量服务。
2. 开启 embeddings 后，按 32 个片段一批计算缺失向量；缓存键包含接口、模型与文本内容的 SHA-256，修改文本会使旧向量失效。
3. 对查询计算向量，做余弦相似度排序，语义候选阈值为 0.15。
4. 用 reciprocal rank fusion 合并关键词与语义排名，返回有来源 metadata 的前若干片段。`search_memory` 默认返回 8 条，可指定 1–20 条。

这里使用 LangChain 的 Retriever、Document 和 OpenAI Embeddings 适配器，但评分逻辑在项目代码中。它不是 BM25、ANN 索引或带重排模型的检索系统。初始记忆选择使用 `memory.ts` 的关键词评分（标题权重更高），不要将其与工具的混合召回混为一谈。

## 效率与准确率的边界

语义集合限制为 2,000 个片段、300 万字符，向量缓存每个 scope 最多保留 2,000 项。缓存降低重复嵌入成本，但向量比较仍线性遍历候选；查询向量每次重新计算。扩大到大型知识库前，需要专门测量、索引与召回评估。

准确率没有固定保证。用代表性问题和人工标注来源衡量 Recall@k、MRR、来源命中率，再结合冷/热缓存延迟及向量请求数量比较。检索到的片段仍须由文件和工具验证；减少无关片段、补足来源和维护过期事实，比直接增加返回条数更有帮助。

语义检索会将查询及候选文档或记忆文本发送到配置的向量接口，首次使用遵循联网审批；费用独立于聊天预算。关闭时关键词检索可继续使用。服务失败或维度变化会报错，不会伪装成语义检索成功。配置入口见 [模型设置](configuration.md)。

## 数据备份、恢复与清理

在 **设置 → 数据与更新 → 数据与诊断** 查看数据库大小、任务数量与安全存储状态。备份使用 SQLite 一致性备份，包含已经提交的 WAL 数据，不要用运行中的数据库主文件复制代替。备份包含任务、附件、记忆和加密凭据，文件本身不是全库加密；请保存在受控位置。项目文件和独立工作树不在数据库备份中，需另行使用 Git 与文件备份。

**恢复数据备份** 会校验完整性、数据表与版本，确认后安排在下次启动应用时恢复，不替换正在使用的数据库。期间不能开始新任务，可以取消待执行恢复。恢复前自动保存 `before-restore-*.sqlite`，再切换数据库。恢复时必须关闭外部数据库连接；较新版本的数据库会拒绝恢复。跨电脑或系统恢复后，原加密凭据可能需要重新连接。

**清理归档超过 30 天的任务** 只处理已归档、已结束且没有关联工作树的任务；需再次确认，并先生成 `before-cleanup-*.sqlite`。删除任务同时清理事件、检查点、工具输出与不再被其他任务引用的附件，保留共享项目记忆及向量缓存。自动生成的安全备份也包含私有数据，应用不会自动删除，请按自己的保留要求管理。

**导出诊断信息** 仅导出版本、系统类型、数据库记录数量、大小、内存与任务数量；不导出提问、文件内容、模型密钥或项目路径。完整故障现场仍需由用户选择性提供。

## 敏感数据保护

Agent 默认不能直接读写 `.env`、私钥、凭据文件和 `.aws` / `.ssh` 等敏感路径；`.env.example`、`.env.sample`、`.env.template` 等模板可以读取。搜索与代码历史也跳过敏感路径；历史恢复不负责恢复被排除的文件。请手动配置真实密钥，需分析时提供脱敏文本。

上下文、工具输出、向量请求和模型协议重放中的常见密钥、密码赋值及私钥块会做文本脱敏。大结果在分页前处理，恢复旧工具结果时也重新处理。命令实时输出缓冲完整行后处理，可能比逐块显示稍晚。该机制不能识别任意编码、拆分或隐藏的秘密，也不能检查图片像素。已批准的主机命令、联网进程和 MCP 服务仍能独立访问外部系统，不能把文本脱敏当作完整 DLP。系统沙箱屏蔽启动时发现的敏感文件，包括依赖和构建目录中的敏感路径；扫描超过 100 万目录项时会拒绝命令。硬链接、启动后新建文件和任意编码的秘密仍需独立控制。

Linux 只允许已识别的系统密钥存储后端持久保存凭据。检测到 `basic_text` 时，会清除本地旧模型配置及 MCP 凭据记录，新密钥只留在会话内存；未知或暂时不可用时保留原加密记录。旧备份仍需自行管理，这不是磁盘取证级安全擦除。

全文搜索在脱敏后匹配，单文件最多 512 KB、单次最多 64 MB，超限需缩小 glob。文件读取偏移以脱敏文本为准，SHA-256 仍对应原文件；不应把占位符写回源文件，包含秘密的整文件替换遇到脱敏占位符会被拒绝。含敏感内容的 Git 差异会从 Agent 输出中省略，仍可人工检查。
