# データ・記憶・検索

## ローカルの保存先

既定の保存先は Electron の appData 配下の `Hikari` です。DB 名は現在の実装に合わせて **`hakari.sqlite`** です。`hikari.sqlite` ではありません。

| OS      | 既定のファイル                                                                           |
| ------- | ---------------------------------------------------------------------------------------- |
| macOS   | `~/Library/Application Support/Hikari/hakari.sqlite`                                     |
| Windows | `%APPDATA%\Hikari\hakari.sqlite`                                                         |
| Linux   | 通常は `~/.config/Hikari/hakari.sqlite`。実際の場所は Electron の appData 設定によります |

`HIKARI_DATA_DIR` で保存先を分けられます。`FORGE_DATA_DIR` は旧設定の互換用です。新しい DB が存在しない場合、旧名の DB を探し、SQLite backup で WAL のコミット済みデータも含めてコピーします。整合性確認後に新しいファイルを公開し、元ファイルを残します。既存の新 DB は上書きしません。

DB は WAL を使います。SQLite の整合性を保つバックアップを使うか、Hikari を終了してからコピーしてください。実行中に主ファイルだけをコピーすると、WAL 内のデータが欠ける場合があります。

## DataGrip で確認する

**SQLite** データソースを作り、実際の `hakari.sqlite` を選択します。ホスト、ポート、アプリのアカウントは不要です。求められた場合は SQLite ドライバーをインストールしてください。調査には読み取り専用接続やコピーを使い、実行中のチェックポイント、権限、version を直接編集しないでください。

各テーブルは `id`、`owner`、`version`、`data`、`updated_at` を持ちます。デスクトップの owner は `local`、業務データは `data` の JSON テキストです。次の読み取り専用クエリで確認できます。

```sql
SELECT id, version, updated_at, data
FROM tasks WHERE owner = 'local'
ORDER BY updated_at DESC LIMIT 20;

SELECT id, data FROM messages
WHERE owner = 'local'
  AND (id LIKE 'memory:%' OR id LIKE 'checkpoint:%');
```

| レコード                              | 用途                                            |
| ------------------------------------- | ----------------------------------------------- |
| `tasks`、`events`、`changes`          | タスク、イベント履歴、変更レビュー              |
| `messages` / `checkpoint:<taskId>`    | 再開用の実行状態                                |
| `messages` / `memory:<scope>`         | プロジェクトの長期記憶                          |
| `messages` / `vectors:<scope>`        | 検索用ベクトルキャッシュ                        |
| `tool_calls` / `output:<taskId>:<id>` | ページ分割された大きなツール結果                |
| `model_configs`                       | 表示設定、暗号化されたモデル設定と MCP 認証情報 |
| `grants`、`workspaces`                | 保存済み承認と最近のプロジェクト                |

OS の安全なストレージが使える場合、モデルキーと MCP トークンを暗号化して保存します。それ以外では現在のプロセスのメモリにのみ保持します。プロジェクトの内容、タスク、記憶、ツール結果を含む DB 全体は暗号化されていません。ベクトルはローカルのキャッシュであり、独立したベクトル DB ではありません。

## 三種類の記憶

| 概念     | 実装                                                                                          | 保存の範囲                                                                                                                       |
| -------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 短期文脈 | `ContextManager` がモデルのメッセージとツールのやり取りを管理し、追加質問に関連履歴を読み込む | 履歴はタスクに残り、復元にはチェックポイントを使う。予算に合わせて文脈を圧縮するため、すべての履歴を毎回モデルへ送るわけではない |
| 作業記憶 | `MemoryManager` が目標、計画、要約、判断、未完了項目を保持し、runner が実行状態を管理する     | `RunnerCheckpoint` にメッセージ、作業記憶、予算、回答待ち質問、ワークフロー段階を保存                                            |
| 長期記憶 | `remember` / `search_memory` で scope ごとにタイトル、内容、出典、期限を保存                  | `LocalPersistence.memories` が SQLite に保存。独立 Worktree は元プロジェクトの scope を使う                                      |

長期記憶は全会話の自動保存ではありません。Agent は承認を受ける `remember` ツールで有用な事実を保存します。**プロジェクトの会話 → メモリーと拡張機能** で確認、編集、削除できます。scope ごとに最大 100 件です。新しいタスクはまずキーワードで関連記憶を選びます。期限切れは確認用に残りますが、検索対象から外れます。

記憶とモデルの要約は参考資料です。古くなったり誤ったりするため、ユーザーの指示や実際のファイル・テスト結果より優先されません。[実行と再開](run-controls.md) も参照してください。

## 検索の経路

コード検索と文書 RAG は別の経路です。`RepositoryIndexer`、ripgrep、`search_code` はファイルの発見、文字列検索、関連パスの順位付けを行います。リポジトリ全体を自動的にベクトル化する機能ではありません。

添付の断片と保存済み記憶は `packages/agent-runtime/src/retrieval.ts` で検索します。

1. 既定では正規化した語句を照合し、ベクトルサービスを呼びません。
2. embeddings を有効にすると、未計算の文書ベクトルを 32 件ずつ処理します。キャッシュの SHA-256 キーには接続先、モデル、本文が含まれ、本文変更で旧ベクトルは無効になります。
3. クエリをベクトル化し、コサイン類似度で比較します。意味検索の候補は 0.15 を超えるものです。
4. reciprocal rank fusion で語句と意味の順位を統合し、出典 metadata とともに上位を返します。`search_memory` は既定 8 件、指定範囲は 1〜20 件です。

LangChain の Retriever、Document、OpenAI Embeddings を使いますが、順位付けはプロジェクト内の実装です。BM25、ANN 索引、再ランキングモデルのパイプラインはありません。開始時の記憶選択は別の `memory.ts` の語句スコアで、タイトルの一致を重く扱います。

## 速度と精度の限界

意味検索の集合は最大 2,000 断片、300 万文字です。scope ごとに最大 2,000 ベクトルを保存します。キャッシュは文書の再計算を減らしますが、類似度比較は候補を線形に走査し、クエリは毎回ベクトル化します。大規模な知識庫には計測、専用索引、検索評価が必要です。

固定の正答率は保証できません。代表的な質問と正解出典を用意し、Recall@k、MRR、出典の命中率、初回・キャッシュ後の遅延、ベクトル API の呼び出し回数を測ります。検索結果はファイルとツールで確認してください。返す件数を増やす前に、無関係な断片を減らし、出典と期限を整えることが役立ちます。

意味検索ではクエリと候補文書・記憶の本文を設定先へ送信し、通信の承認が適用されます。料金は会話予算とは別です。無効時も語句検索は利用できます。接続障害や次元変更はエラーとして通知し、意味検索が成功したようには扱いません。設定は [モデル設定](configuration.md) を参照してください。

## バックアップ、復元と診断

**設定 → データと更新 → データと診断** でサイズ、件数、安全な認証情報ストアの状態を確認できます。SQLite の整合性バックアップには WAL のコミット済みデータも含まれます。タスク、添付資料、メモリー、暗号化された認証情報を含みますが、ファイル全体は暗号化されません。プロジェクトや作業ツリーは Git 等で別途保存してください。

復元は整合性、テーブル、バージョンを検証して次回起動時に適用します。先に現在のデータを `before-restore-*.sqlite` に保存します。再起動または予約解除まで新しいタスクは開始できません。外部の DB 接続を閉じてください。新しいスキーマは拒否され、別の端末では認証情報の再設定が必要な場合があります。

クリーンアップは作業ツリーがない、30日以上前にアーカイブした終了済みタスクのみ対象です。確認後に `before-cleanup-*.sqlite` を作成し、イベント、チェックポイント、ツール結果、参照されていない添付資料を削除します。共有メモリーとベクトルは残ります。退避バックアップの保管期限は利用者が管理してください。診断はバージョン、件数、サイズ、リソース使用量のみで、プロンプト、本文、プロジェクトパス、認証情報を含みません。

## 機密データの扱い

`.env`、秘密鍵、認証情報、`.aws`、`.ssh` 等は直接アクセス、検索、コード履歴の対象外です。設定例やテンプレートは読み取れます。秘密情報は手動で設定し、解析用には伏せ字の抜粋を渡してください。除外ファイルは履歴から復元できません。

コンテキスト、保存済みツール結果、埋め込み要求、モデル固有の再送データ内の一般的な認証情報や秘密鍵を伏せ字にします。コマンドのライブ出力は行単位で処理します。任意の符号化、分割された秘密情報、画像ピクセルを保証する DLP ではありません。承認済みのホストコマンド、ネットワーク処理、MCP は別途制御が必要です。OS サンドボックスは検出済みパスを隠しますが、依存・ビルドディレクトリ内の機密パスも検査し、100万項目を超える走査は拒否します。ハードリンク、起動後の新規ファイル、任意の符号化には追加対策が必要です。

Linux の未知・利用不可ストアと `basic_text` ではモデルと MCP の認証情報を永続化しません。`basic_text` を検出した場合は旧モデル設定と MCP 認証情報レコードを削除します。未知または一時的にロックされたストアでは既存レコードを保持し、新しい値はセッションメモリのみで利用します。フォレンジック上の完全消去ではなく、旧バックアップは別途管理してください。

検索は伏せ字処理後の本文を対象とし、1ファイル512 KB、1回64 MBまでです。超過時は glob を絞ってください。読み取りオフセットは処理後の本文、SHA-256 は元ファイルに対応します。秘密情報を含む元ファイルへの伏せ字入り全置換は拒否されるため、限定的なパッチを使用してください。機密を含む Git 差分は Agent 出力から除外し、手動で確認します。
